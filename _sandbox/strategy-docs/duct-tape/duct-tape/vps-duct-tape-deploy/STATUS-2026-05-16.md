## Key decisions / behaviors

1. **Form is NOT touched.** `quick-scan-form.tsx` still sends `siteName: "AnyWho"` on first submit and `siteName: "Zabasearch"` on "none of these." The edge function ignores the requested siteName when a scan history exists and instead picks the next un-run scraper from the sequence.
2. **Sequence is `anywho → fastpeoplesearch → zabasearch`** per user instruction (FPS before Zaba on "none of these"). Sequence stops on first match.
3. **State-only retry** lives in the bridge (`scraper-lab-client.ts`), not the worker. When a job returns 0 matches with city present, the bridge fires a second job with `city: undefined`. Rationale: city/zip is the user's location identifier, not a filter — broker sites often list under canonical metro names (66210 → Overland Park, not USPS "Shawnee Mission").
4. **`SCRAPER_LAB_POLL_MAX_SEC=75`** (down from 150) to leave headroom for sequence + state-only retry within Supabase's edge timeout. Worst-case per scraper now = 150s (with-city + state-only). Worst-case sequence (two scrapers, both retrying) could approach 300s — exceeds Supabase wall. **Live risk.** See follow-ups.
5. **FPS Cloudflare blocking is a known risk** per plan §1 non-goal. Currently aggravated by FPS subprocess SIGKILL — see Issue 1.

### Issue 1 — FPS nodriver dies with code 137

**Symptom from worker terminal:**
```
🔍 FPS - Direct fetch status=403 class=blocked len=99686
🔍 FPS - Trying nodriver (python3 /Users/.../scripts/fps_nodriver_smoke.py)
🔍 FPS - nodriver: no JSON (code=137). stderr:
(no stderr)
🔍 FPS - transport=synthetic_blocked classification=blocked http=403
```

**What we ruled out / confirmed:**
- User reports Chrome for Testing **did** launch when they previously fingerprint-warmed FPS many times — so the setup is known-good historically.
- User's `CHROME_FOR_TESTING_BIN` points to `/Users/JamesO/Library/Caches/ms-playwright/chromium-1200/chrome-mac-arm64/Google Chrome for Testing.app/Contents/MacOS/Google Chrome for Testing`.
- `chromium-1200` directory exists on disk; the exact binary path was not yet verified (left as the last unfinished command of the session — see Next Steps).
- Running the python script alone (from interactive Terminal) opened Chrome successfully in a prior session.

**Hypotheses, in likelihood order:**
1. **Stale Playwright cache path** — if Playwright auto-updated, `chromium-1200` may have been replaced or supplemented by a newer `chromium-XXXX`. The exact `.app` bundle inside may have been pruned. **Run** `find /Users/JamesO/Library/Caches/ms-playwright/chromium-1200 -name "Google Chrome for Testing" -type f 2>/dev/null` to confirm.
2. **Worker-subprocess environment differs from interactive shell** — when the worker (running under Deno) spawns python3 via subprocess, `PATH`/`PYTHONPATH` may resolve to a different interpreter that doesn't have the required modules. Worth testing by running `python3 fps_nodriver_smoke.py` in the **same terminal** the worker is running in (not a fresh terminal).
3. **macOS TCC / Automation permission** — Deno-spawned subprocesses may not inherit GUI-launching permissions. If the worker was originally launched from a Terminal with prior accessibility grants and is now launched from a different shell context, macOS may SIGKILL the GUI spawn.

### Issue 2 — Worker doesn't write job failures to Redis

Symptom: bridge `pollSec=75` times out even though worker logged FPS error in <2 seconds. Indicates `processJob` in `vanyshr-scraper-lab/apps/scraper-worker/main.ts` doesn't catch and persist scraper exceptions back to Redis job state. **Out of scope for pilot — but it makes FPS blocking 15× more expensive in wall time.** Workaround: keep FPS out of sequence or rely on bridge timeout.
